- `nen/workflow.json` gains `commits.stripInjected` (zheref/nen#594): an OPT-IN list of trailer keys, empty by default, that the `nen scaffold init` commit-msg hook may remove from a message's trailer block when a hook added them inside a commit `nen commit write` or `nen wc squash` started — Cursor's cloud agents append `Co-authored-by:` in a `prepare-commit-msg` nobody can switch off, and until now no nen-scaffolded repository could take a commit from one. The strip runs only when `NEN_COMPOSED_TRAILER_KEYS` is set (the two verbs set it on their child `git commit`), never touches a key the composed message carried, never admits a refused key, never amends, and reports every removal on stderr and in `<git dir>/nen-stripped-trailers`. A key the policy admits under `commits.allowedAttributionTrailers` is refused in the list by pointer. Without the opt-in, docs/USAGE.md now says plainly that a hook-injected refused key is a refusal with no sanctioned way around it, pointing to zheref/hatsu's `docs/AGENT-ATTRIBUTION.md` for the stop.
- Behaviour changes: `nen commit write` and `nen wc squash` gain exit `4` — committed, and the hook stripped a hook-injected key — with `3` (a refused key still on the commit) winning over it and it over `0`; their `--json` gains `stripped: [key, ...]`, appended last (`null` on a dry run, `[]` when nothing was stripped). Both now ask `git rev-parse --git-dir` before the commit and run it with `NEN_COMPOSED_TRAILER_KEYS` set. A failed commit under a non-empty list adds a hint that the hook may predate it, and the exit-3 line for a hook-added key names the opt-in as a second remedy. Generated hooks are unchanged until a repository lists a key and regenerates with `nen scaffold init … --force`: with the list empty the hook is byte-identical, so `scaffold init` keeps reporting it `unchanged`. `templates/workflow.json` writes `"stripInjected": []` into a fresh policy.
