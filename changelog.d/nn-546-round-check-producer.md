- Round checks can be bound to their producer (zheref/nen#546): a reviewer in `nen/gates.json` may state `round_check_producer`, either `{ "app": { "slug": "<slug>", "id": <n> } }` (`id` optional) or `{ "workflow": { "path": ".github/workflows/<file>.yml", "repository": "<owner/name>", "events": ["<event>", ...] } }`, and then a `round_check_pattern` `SUCCESS` is that reviewer's round only when GitHub records the declared producer: the App that created the check suite (`checkSuite.app`, REST `app`), or, for a workflow, a `github-actions` suite whose run (`actions/runs?check_suite_id=`) has that path, repository and event. A check's name is not its identity, so a pull request's own job named like the reviewer's check no longer clears the round. A name-matching `SUCCESS` from another producer stays owed as `round-check-producer-mismatch`, and one whose producer evidence was not read as `round-check-producer-unverified`. Both carry a `producer` detail in `owedRounds[]` and in row 4's reason. The same test applies at head, at an earlier head under `bounded` (an impersonating run is passed over with a warning and the walk keeps looking) and to the in-flight rule, and through `round_quorum`, `--explain` round counts and `watch until --until review-posted`. A malformed producer is refused at load by pointer, as is a producer on a reviewer with no `round_check_pattern`. `events` is required and non-empty, because on `pull_request` GitHub runs the workflow file as the pull request changed it. `docs/USAGE.md` states the trust boundary and the adoption steps. nen's own `nen/gates.json` declares no producer.
- Behaviour changes: none for a file without `round_check_producer`. Its rounds read by name and `SUCCESS` exactly as before, the state blob gains no key, and no extra call is made. The PR snapshot's GraphQL check-run selection adds `checkSuite.databaseId` and `checkSuite.app.databaseId`, both `checks:read`, and parsed check runs gain optional `appId` and `checkSuiteId`. A file carrying the key is refused by every earlier nen as an unknown key (zheref/nen#310), never read by name alone. A `workflow` producer makes one `actions/runs` read per name-matching `SUCCESS` check suite (at most 10 per evaluation), needs `actions:read`, adds `round_check_workflow_runs` to the state, and turns a failed read into a `meta.warnings` entry and an unverified round. A `round_quorum` member whose `SUCCESS` at head is not counted reports state `unsuccessful` with a `producer` field. `earlier_round_checks` entries gain optional `app_slug`, `app_id` and `check_suite_id`. `nen pr next-blocker` reads `gh pr view`, which carries no App, so a constrained round reads unverified there.
