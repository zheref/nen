- Round checks can be bound to their producer (zheref/nen#546). A reviewer in `nen/gates.json` may state `round_check_producer`, either `{ "app": { "slug": "<slug>", "id": <n> } }` or `{ "workflow": { "path": ".github/workflows/<file>.yml", "repository": "<owner/name>", "events": ["pull_request_target", ...] } }`. A `round_check_pattern` `SUCCESS` is then that reviewer's round only when GitHub's record names that producer: for `app`, the App that created the check suite, by slug **and** id (`id` is required); for `workflow`, a `github-actions` suite whose run (`actions/runs?check_suite_id=`) has that path, repository and event, names this pull request and its base branch in `pull_requests[]`, and has the check among its jobs (`actions/runs/{id}/jobs`). A check's name is not its identity, so a pull request's own job named like the reviewer's check no longer clears the round, nor does a check a token wrote into a trusted suite or a run made for another pull request. Events that run the pull request's own revision (`pull_request`, `push`, `merge_group`, `pull_request_review`, `pull_request_review_comment`, `workflow_dispatch`) are refused at load unless the workflow states `"trusts_pull_request_revision": true`. While that opt-in is in force, `nen schema check` and `nen pr ready` warn. A name-matching `SUCCESS` from another producer stays owed as `round-check-producer-mismatch`, and one whose producer evidence was not read as `round-check-producer-unverified`. Both carry a `producer` detail in `owedRounds[]` and in row 4's reason. A run known to come from another producer is dropped before the latest-by-name reduction, so it can neither hide the reviewer's run in flight nor replace its `SUCCESS`. The same test applies at head, at an earlier head under `bounded` (an impersonating run is passed over with a warning), to the in-flight rule, through `round_quorum`, in `--explain` round counts, and in settlement for `watch until --until review-posted`. A malformed producer is refused at load by pointer, including an explicit `null`, a producer with no `round_check_pattern` and a producer on a `wake: "event"` reviewer. `docs/USAGE.md` states the trust boundary, what remains, and the adoption steps. nen's own `nen/gates.json` declares no producer.
- Behaviour changes: none for a file without `round_check_producer`. Its rounds read by name and `SUCCESS` exactly as before, the state blob gains no key, and no extra call is made. The PR snapshot's GraphQL check-run selection adds `checkSuite.databaseId` and `checkSuite.app.databaseId`, both `checks:read`, and parsed check runs gain optional `appId` and `checkSuiteId`. Every earlier nen refuses a file carrying the key as an unknown key (zheref/nen#310); none reads it by name alone. A `workflow` producer needs `actions:read`. It spends at most 20 reads an evaluation, one per run lookup and one per jobs page, and reads jobs only for a run that could match. It adds `pr_number` and `round_check_workflow_runs` to the state, and turns a failed read into a `meta.warnings` entry and an unverified round. A `round_quorum` member whose `SUCCESS` at head is not counted reports state `unsuccessful` with a `producer` field. `earlier_round_checks` entries gain optional `app_slug`, `app_id`, `check_suite_id` and `check_run_id`. `nen pr next-blocker` reads `gh pr view`, which carries no App, so a constrained round reads unverified there.
