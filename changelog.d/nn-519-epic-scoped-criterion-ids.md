- Epic-scoped criterion ids (zheref/nen#519): `nen issue criteria`, `nen issue body-check` and `nen pr converge` (and `pr body-check --criteria`/`--criteria-from`, `pr merge --delivery`) now share one criterion id grammar, and Akatsuki's `- AC-12-001: …` rows are criteria with their whole id -- `AC-12-001`, never truncated to `AC-12` -- where they used to be listed as unrecognised and the issue read not verifiable. A verify row `<CODE>#<N>/AC-12-001` matches that criterion and `<CODE>#<N>/AC-12` does not. With no catalogue the id is one number or several joined by hyphens; with a catalogue (`--requirements-from` / `--catalogue`) the shape is the group its `rows.acceptance.pattern` opens right after the prefix, never a binary default, so Hatsu's `^- AC-([0-9]+): …` keeps reading `AC-{n}` only. The bold `- **AC-1**:` form, `AC-01` read as `AC-1`, and the `SC-`, `AS-`, `OQ-` rows are unchanged.
- Behaviour changes: a `hatsu.issue-sections/v1` catalogue whose `rows.acceptance.pattern` opens no group right after `<ID>-` is now refused at exit 2 naming that field, where its acceptance id used to be read as `<ID>-<n>` regardless. A list row such as `- AC-1-2: …` that used to be unrecognised (blocking `pr converge`) is now the criterion `AC-1-2` when no catalogue is given. A criterion's `--json` `number` is its id's last number (`AC-12-001` is 1); rows are matched by `id`. `--criteria AC-01` is now read as `AC-1` where it used to be refused at exit 2. A single-run id is read by value as text (leading zeros dropped, never through a float); a row whose last digit run passes nine digits is unrecognised. A closing issue stating one criterion id on two rows now blocks `pr converge`, `pr body-check --criteria*` and `pr merge --delivery` (`<issue>: duplicate criterion id <id> at lines …`, or `at positions …` for a `--criteria` list) where one verify row used to clear both. The verify rows' prefix is now the catalogue's acceptance prefix: under a catalogue whose prefix is not `AC`, a row `| AC-1 | … |` that used to cover `CR-1` is reported malformed; a verify cell whose id (after any `<owner/name>#<N>/` qualifier) passes 64 characters is never matched, and an issue row whose id span passes 64 characters is unrecognised. A catalogue's acceptance id group must keep to the safe subset USAGE names (digit classes, `-`, bounded quantifiers; a variable digit run ends at a `-` or the end; a nested quantifier only in a `-`-led or `-`-ended group; no named group or backreference), else exit 2. `issue criteria`'s summary says `duplicate id(s)` where it said `duplicate number(s)`, and an epic-scoped `row-order` miss names the expected id within its leading group.
