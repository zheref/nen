- `nen run import --id <run-id> [--from <file>]` reads Hatsu's futon run manifest (`hatsu.futon.run/v0.2`, or v0.1) from `<git-common-dir>/hatsu/futon/run-<id>.json` into nen's `nen.run/v0.1` manifest (zheref/nen#486 AC-5), so one manifest owns a batch run and Hatsu can retire its second one. It reuses the `run start`, `append` and `park` plans: every PR is read live, issue numbers become `<owner/name>#<N>`, and the idle decisions become `idleAnswers`. It is idempotent (`unchanged` on a re-import) and never writes the Hatsu file. An unread PR, a PR older than the run, or a contradiction with the manifest nen holds refuses the whole import at exit 1, with nothing written. `run start|append|park|verify` (AC-1 to AC-4) shipped in #484/#498 and are unchanged.
- `run append --issue` and `run park --issue` now record one spelling, `<owner/name>#<N>`. A `<CODE>#<N>` is resolved through `--repo`'s `nen/repos.json`, so an append after an import names the same issue. A code the registry does not resolve to one `owner/name` is exit 2. Behaviour change: a manifest that already holds code-form issues conflicts with a re-append in either form. Re-import, or edit the manifest once.
